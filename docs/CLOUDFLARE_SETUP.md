# Cloudflare D1 setup (legacy gateway)

> **Legacy (Vercel only).** This page describes the Phase 2 setup where Next.js ran on **Vercel** and reached D1 through the gateway Worker. The app now runs on **Cloudflare Workers** with a native D1 binding — follow [MANUAL_SETUP.md](MANUAL_SETUP.md) and [CLOUDFLARE_DEPLOYMENT.md](CLOUDFLARE_DEPLOYMENT.md) instead. Keep this page only until Vercel is retired. Note: the database commands below now run from the project root (`wrangler.jsonc`), e.g. `npm run db:migrate:remote`.

How the daycare app reaches its database, and every step to set it up locally and in production.

```
Browser ──▶ Next.js on Vercel (server actions / server components)
                │  HMAC-SHA256 signed HTTPS (D1_GATEWAY_SECRET)
                ▼
          D1 gateway Worker  (cloudflare/d1-gateway, binding "DB")
                │
                ▼
          Cloudflare D1  "daycare-db"
```

**Why a gateway Worker?** D1 is only reachable natively from Cloudflare Workers. Cloudflare's D1 REST API is meant for administrative use and is rate-limited for the account, so it isn't suitable for live app traffic. The Worker is a small, authenticated SQL transport: it accepts only requests signed with a shared secret, refuses schema changes (`CREATE`/`DROP`/`ALTER`/`PRAGMA`/…), and runs multi-statement writes as one atomic D1 batch. **Tenant isolation and role checks happen in the Next.js service layer**, so the secret must exist only on the Vercel server and in the Worker — never in browser code or a `NEXT_PUBLIC_*` variable.

---

## 1. Prerequisites

- Node.js 20.9+ (22 LTS recommended) and the project dependencies: `npm install`
- Gateway Worker dependencies (includes Wrangler 4): `npm --prefix cloudflare/d1-gateway install`
- A Cloudflare account. Log Wrangler in once: `cd cloudflare/d1-gateway && npx wrangler login`

## 2. Create the D1 database

```bash
cd cloudflare/d1-gateway
npx wrangler d1 create daycare-db
```

Wrangler prints a `database_id` (a UUID). It is an identifier, not a secret.

> Use a separate database per environment if you want isolated staging data, e.g. `daycare-db-staging`, with its own Worker (see step 10).

## 3. Point the Worker at the database

Edit `cloudflare/d1-gateway/wrangler.jsonc` and replace the placeholder:

```jsonc
"database_name": "daycare-db",
"database_id": "<the id from step 2>",
"migrations_dir": "../../drizzle/migrations"
```

`migrations_dir` points at the SQL generated by Drizzle at the repo root, so the app schema (`lib/db/schema`) and the database never drift.

## 4. Create the gateway secret

Generate one random value (at least 32 characters) and use it in **both** places:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

| Where | Name | How |
|---|---|---|
| Deployed Worker | `GATEWAY_SECRET` | `cd cloudflare/d1-gateway && npx wrangler secret put GATEWAY_SECRET` (paste when prompted) |
| Vercel project | `D1_GATEWAY_SECRET` | Vercel → Settings → Environment Variables (step 8) |
| Local Worker | `GATEWAY_SECRET` | `cloudflare/d1-gateway/.dev.vars` (copy `.dev.vars.example`; git-ignored) |
| Local app | `D1_GATEWAY_SECRET` | `.env.local` (git-ignored) |

Use a **different** secret for local development than for production. Never commit either.

## 5. Apply the migrations (explicitly — never automatic)

Migrations are plain SQL files in `drizzle/migrations`, generated from the TypeScript schema. Nothing applies them automatically — not `npm run dev`, `npm run build`, a Vercel deploy, or the Worker deploy.

```bash
# Local D1 (used by `wrangler dev`)
npm run db:migrate:local

# Remote D1 — Wrangler lists the pending files and asks for confirmation
npm run db:migrate:remote
```

Check status at any time:

```bash
npm --prefix cloudflare/d1-gateway run migrations:list:local
npm --prefix cloudflare/d1-gateway run migrations:list:remote
```

**Changing the schema later:** edit `lib/db/schema/*`, run `npm run db:generate`, review the new SQL file in `drizzle/migrations`, commit it, apply locally, run the tests, then apply remotely. Review any migration that drops or rewrites a table before applying it to production, and take a backup first (step 10).

## 6. Deploy the gateway Worker

```bash
npm run gateway:deploy
```

Wrangler prints the Worker URL, e.g. `https://daycare-d1-gateway.<your-subdomain>.workers.dev`. Check it:

```bash
curl https://daycare-d1-gateway.<your-subdomain>.workers.dev/health
# {"ok":true,"service":"daycare-d1-gateway"}
```

Unsigned or wrongly-signed requests to `/v1/query` get `401`. Requests older than 60 seconds are rejected, so the Vercel server clock must be accurate (it is).

## 7. Seed sample data (development only)

The seed creates the sample tenant **Little Stars Daycare** (34 children including Amari Young, Jayden Smith, Sophie Jones, Noah Brown, Emma White, Liam Carter, Olivia Martin and Ethan Wilson; staff including Sarah Wilson, Michael Carter, Jasmine Green and David Thompson; guardians; ~10 weekdays of attendance and time-clock history plus today), a second sample tenant for isolation checks, and links **you** as `DAYCARE_OWNER`.

```bash
npm run db:seed:local -- --admin-email you@example.com --admin-name "Your Name"
```

- The owner is linked by `auth_provider_id`. With the current password login that is `password:usr_bootstrap` (the default). Pass `--admin-auth-id` if your identity differs.
- Email/name fall back to `SEED_ADMIN_EMAIL`/`SEED_ADMIN_NAME`, then `AUTH_EMAIL`/`AUTH_USER_NAME` from `.env.local`. No email is hard-coded anywhere in the app.
- Staff PINs are stored only as bcrypt hashes. The demo PINs are printed to your terminal.
- The seed only uses `INSERT OR IGNORE`, so it never deletes or overwrites data. For a clean local demo day, delete `cloudflare/d1-gateway/.wrangler`, then migrate and seed again.
- It never runs automatically. Seeding a **remote** database requires naming it: `npm run db:seed:remote -- --admin-email you@example.com --confirm-remote daycare-db`. Do this only for a development/staging database, never for a production database that holds real families.

**Production without sample data:** insert your organization, its `organization_branding` row, a `users` row for your identity (`auth_provider_id = 'password:usr_bootstrap'`) and an `organization_memberships` row with role `DAYCARE_OWNER`, using `npx wrangler d1 execute DB --remote --command "…"`. An admin UI for creating tenants is Phase 3.

## 8. Vercel environment variables

Vercel → Project → **Settings → Environment Variables**:

| Variable | Production | Preview | Development | Notes |
|---|:-:|:-:|:-:|---|
| `D1_GATEWAY_URL` | ✅ | ✅ | ✅ | Deployed Worker URL, no trailing slash. Preview may point at a staging Worker. |
| `D1_GATEWAY_SECRET` | ✅ | ✅ | ✅ | Same value as that Worker's `GATEWAY_SECRET`. Mark **Sensitive**. |
| `SESSION_SECRET` | ✅ | ✅ | ✅ | Existing. Different value per environment. Sensitive. |
| `AUTH_USERS` | ✅ | ✅ | ✅ | JSON array of `{username,passwordHash,name?}`. Paste bcrypt hashes as-is (no `\$`). Prefer this over the single-user vars. |
| `DEMO_DATA` | optional | optional | optional | Omit to auto-use fixture demo when `D1_GATEWAY_*` are unset. Set `0` to require a real DB. |
| `AUTH_USERNAME` / `AUTH_PASSWORD_HASH` | legacy | legacy | legacy | Only when `AUTH_USERS` is unset. Paste hash as-is (no `\$`). |
| `AUTH_USER_NAME` | optional | optional | optional | Legacy single-user display name. |
| `AUTH_EMAIL` | optional | optional | optional | Legacy single-user email. |

"Development" is what `vercel env pull` / `vercel dev` use; for plain `npm run dev` use `.env.local`. **Redeploy** after changing variables. Do not add `SEED_*` variables to Vercel — the app never reads them.

If Preview deployments share the production Worker and secret, they read and write **production data**. For safety, give Preview its own Worker + D1 database (step 10) or leave the Preview variables unset until you have one.

## 9. Local development

```bash
cp .env.example .env.local                 # fill in SESSION_SECRET, AUTH_USERS (or AUTH_PASSWORD_HASH), D1_* (see below)
cp cloudflare/d1-gateway/.dev.vars.example cloudflare/d1-gateway/.dev.vars   # set GATEWAY_SECRET
npm run db:migrate:local
npm run db:seed:local -- --admin-email you@example.com
npm run gateway:dev                         # terminal 1 → http://127.0.0.1:8787
npm run dev                                 # terminal 2 → http://localhost:3000
```

In `.env.local`: `D1_GATEWAY_URL=http://127.0.0.1:8787` and `D1_GATEWAY_SECRET=` the same value as `GATEWAY_SECRET` in `.dev.vars`. Local D1 data lives in `cloudflare/d1-gateway/.wrangler/` (git-ignored) and never touches your Cloudflare account.

On Windows use `copy` instead of `cp`.

## 10. Operations: staging, backups, secret rotation, troubleshooting

**Staging / Preview database.** Create a second database (`npx wrangler d1 create daycare-db-staging`) and add a Wrangler environment to `wrangler.jsonc`:

```jsonc
"env": {
  "staging": {
    "name": "daycare-d1-gateway-staging",
    "d1_databases": [
      { "binding": "DB", "database_name": "daycare-db-staging", "database_id": "<staging id>", "migrations_dir": "../../drizzle/migrations" }
    ]
  }
}
```

Then, from `cloudflare/d1-gateway`: `npx wrangler secret put GATEWAY_SECRET --env staging`, `npx wrangler deploy --env staging`, `npx wrangler d1 migrations apply DB --remote --env staging`. Use the staging Worker URL and secret for the Vercel **Preview** environment.

**Backups.** D1 Time Travel keeps point-in-time history (30 days on paid plans). Before a risky remote migration, note a restore point: `npx wrangler d1 time-travel info daycare-db`. Export a copy with `npx wrangler d1 export daycare-db --remote --output backup.sql` (keep it private — it contains children's data).

**Rotating the gateway secret.** Generate a new value → `npx wrangler secret put GATEWAY_SECRET` → update `D1_GATEWAY_SECRET` in Vercel → redeploy Vercel. Requests fail with "database temporarily unavailable" for the minute between the two steps.

**Troubleshooting**

| Symptom | Likely cause |
|---|---|
| "We couldn't load this page" + server log `D1 gateway unreachable` | `D1_GATEWAY_URL` wrong, Worker not deployed, or `gateway:dev` not running locally. |
| Server log `D1 gateway error UNAUTHORIZED` | `D1_GATEWAY_SECRET` ≠ Worker `GATEWAY_SECRET`, or secret shorter than 32 characters. |
| Server log mentions `no such table` | Migrations not applied to that database (step 5). |
| Signed in but sent to **/no-access** | No `users` row with your `auth_provider_id`, or no ACTIVE membership in an ACTIVE/TRIAL organization. Run the seed (dev) or insert the rows (step 7). |
| Kiosk/time clock says "PIN not recognised" | That staff member has no PIN set, or a different one. Set it under Staff → Edit. |

Raw database errors are only written to server logs; users see a short, generic message.
